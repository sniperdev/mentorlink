MentorLink Architecture Review

Tutor-matching platform: a Next.js frontend, a Spring Boot auth-service that issues JWTs, and a Spring Boot mentorlink-backend (tutor profiles and subjects) acting as an OAuth2 resource server, each with its own PostgreSQL database.

Data Architecture

Four tables in two databases. Both user_id columns point at auth_db.users.id by convention only. There is no foreign key and no synchronisation, so no relationship lines are drawn.

Narrative

The system is split along a sensible business line. auth-service owns identity (users, passwords, tokens) in auth_db. mentorlink-backend owns the tutoring catalogue (tutor profiles, subjects) in tutor_db and trusts JWTs signed with a shared HS256 secret. The two Spring services never call each other; their only coupling is the secret and the role claim string. Inside each service the code follows a clean controller → service → repository → mapper layering, with records as DTOs and one consistent ApiError body.

The architecture's weak points are the seams between the parts, not the parts themselves:

  • Tokens go out as cookies but are read back only from the Bearer header.
  • The frontend's tutor type expects identity data (names, email) that lives in the other bounded context.
  • No process creates TUTOR or ADMIN users.
  • Tests disable Flyway, so the shipped schema is never exercised before deploy.

Operationally, the deployment is defined twice (CI images plus three webhooks, and a compose file that builds from source), there is no application logging, and secrets and routing live only in Coolify.

Separation of Concerns

Strength
Clean per-feature layering with explicit mappers

Each backend feature (tutors/, subjects/) separates controller, service, repository, entity, DTO records and a mapper (SubjectMapper, TutorProfileMapper). Controllers contain no business rules and entities never leave the service layer.

Concern
Authentication use case writes HTTP cookies

AuthService.register/login take an HttpServletResponse and call CookieService directly (AuthService.java:29,44,55-65). Credential checking, token issuance and token transport are fused into one method. Changing the transport (cookie, response body, BFF), which Risk 1 requires, therefore means changing the use case itself.

Concern
Frontend UI consumes raw API responses without a mapping layer

features/tutors/api/tutor.api.ts returns response.data typed as a hand-written TutorSummary, and TutorCard renders it directly. Nothing checks or converts the response at the boundary, even though zod is already a dependency.

Cohesion and Coupling

Strength
Small, cohesive feature packages and no runtime coupling between services

Packages are organised by capability (users, auth/refresh, tutors, subjects), and no package cycles were found by import inspection. Neither Spring service has an HTTP client for the other, so they have no synchronous dependency.

Risk
Implicit token contract between auth-service and backend

The services agree on the signing secret, the algorithm, sub as a UUID, and the role claim holding a UserRole enum name. That last point is duplicated as two separate enums (auth users/model/UserRole.java, backend security/UserRole.java). The backend calls UserRole.valueOf(role) (SecurityCurrentUserProvider.java:19), so a renamed or added role, or a missing claim, causes 500s. This contract is not documented or tested anywhere.

Concern
Copy-pasted cross-cutting code

ApiError, GlobalExceptionHandler, ConflictException, ResourceNotFoundException, AuditableEntity and JpaAuditioningConfig exist as identical copies in both services. Duplication is a fair trade-off for keeping the services independent, but the error format, which is a public contract, can now drift silently.

Layered Architecture

Strength
Consistent dependency direction

Controller → Service → Repository holds in both services. Responses are DTO records built by mappers, not JPA entities, and Hibernate runs with open-in-view: false and ddl-auto: validate.

Concern
Application layer depends on servlet types

AuthService imports jakarta.servlet.http.HttpServletResponse, so the service layer depends on the web layer. The token logic cannot be unit-tested or reused without the servlet API.

Hexagonal Architecture / Ports and Adapters

Strength
CurrentUserProvider is a real port

TutorProfileService depends on the CurrentUserProvider interface, and SecurityCurrentUserProvider is the Spring Security adapter. The domain service has no knowledge of JWTs, which keeps TutorProfileServiceTest simple.

Concern
Token delivery has no port

There are few external integrations, so full hexagonal structure is not warranted. The exception is token issuance and delivery: it is the part most likely to change (cookie, Bearer, BFF, asymmetric keys), yet it is wired as concrete classes (JwtService, CookieService) inside the use case.

Scalability

Strength
Stateless services with local token verification

Both security chains use SessionCreationPolicy.STATELESS, and the backend verifies JWTs locally without calling auth-service, so both scale horizontally. The frontend caches reads with React Query (5-minute stale time).

Concern
Unbounded list endpoints

GET /api/v1/tutors and GET /api/v1/subjects return findAll() with no pagination (no Pageable anywhere). This is fine at today's data volume, but it is a breaking API change once it is needed.

Concern
Unbounded growth and no backpressure on auth

Every login and registration inserts a refresh_tokens row that is never read, revoked or deleted. Nothing rate-limits /auth/login, and each BCrypt check is deliberately CPU-expensive.

Observability

Strength
Health endpoints exist

Spring Boot Actuator exposes health and info in both services, and /actuator/health is explicitly permitted in both security chains.

Concern
No application logging, metrics or correlation

Neither service has a single log statement (no @Slf4j or LoggerFactory). Failed logins, conflicts and authorization denials leave no trace, nothing is structured or tagged with a request ID, and no metrics endpoint is exposed. Diagnosing the auth handoff problem in a running environment would be guesswork.

Concern
Some errors escape the error model

Exceptions thrown inside JwtAuthenticationFilter (deleted user, UserService.java:47) and DataIntegrityViolationException from concurrent creates bypass @RestControllerAdvice. They surface as Spring's default error body, with no log line.

Security

Strength
Sound credential and token storage primitives

Passwords use BCrypt. Refresh tokens are 256-bit SecureRandom values stored only as SHA-256 hashes. Cookies are HttpOnly, Secure and SameSite=Lax. Authorization is centralised: URL rules plus @PreAuthorize on the two write endpoints. Secrets come from environment variables, and compose refuses to start without them.

Risk
Token transport mismatch breaks the auth flow

auth-service delivers tokens only as cookies (CookieService.java:18-66) with an empty response body. The backend's resource server reads only Authorization: Bearer (SecurityConfiguration.java:41), and the axios client sends neither (lib/api/client.ts:4). The protected endpoints cannot be used from the web app. Quick fixes, such as returning the token to JavaScript and keeping it in localStorage, would weaken XSS resistance. The fix needs a deliberate design decision.

Risk
Symmetric shared signing key, no issuer or audience checks

Both services hold the same HS256 JWT_SECRET, so anything that can read the backend's environment can mint tokens for any user and role. JwtConfiguration builds a NimbusJwtDecoder without iss or aud validation. Keys cannot be rotated without a coordinated restart of both services.

Concern
Insecure-design gaps in the auth lifecycle

Login ignores UserStatus, so BLOCKED users still get tokens (AuthService.java:44-53). There is no rate limiting or lockout, no refresh, no logout or revocation, and no role-management or privileged-account provisioning.

Concern
Network boundary and database credential isolation

docker-compose.coolify.yml publishes all three services on host ports (18080–18082) instead of one entry point. Both services connect with the same mentorlink database user, which can reach both auth_db and tutor_db, so database-per-service is not enforced by credentials. CORS is hard-coded to http://localhost:3000 (WebConfig.java:13). Exposure and TLS of the live deployment are open.

Concern
CSRF is disabled in both chains

Disabling CSRF is correct for a Bearer-only API. If the fix for the transport mismatch makes the backend accept the cookie, CSRF protection must come back at the same time.

Reliability

Strength
Database readiness gating and restart policy

Postgres has a pg_isready healthcheck, both services wait on condition: service_healthy, and every container uses restart: unless-stopped.

Concern
Application containers have no healthcheck

Actuator health exists, but neither the Dockerfiles nor the compose file define a healthcheck for the frontend, backend or auth-service. Coolify cannot tell a crashed-but-running JVM from a healthy one, and the frontend's depends_on gates only on container start.

Concern
Single Postgres instance for both services

One instance is a single point of failure for the whole platform. That is acceptable for the current LAN/test environment, but it should be an explicit decision before any wider rollout.

Resilience

Strength
Failure isolation between identity and catalogue

The backend never calls auth-service, so an auth outage does not affect public browsing or the validation of already-issued tokens. The blast radius is limited to new logins.

Concern
No backup, restore or recovery objectives

All data sits in one Docker volume (mentorlink_postgres_data), with no backup job, restore procedure, RTO or RPO. Because accounts cannot be re-provisioned automatically, losing or recreating the volume means rebuilding test users by hand.

Concern
Frontend hides failures

FeaturedTutorsSection handles only isLoading. A backend failure, after one React Query retry, renders an empty list instead of an error state, so outages look like "no tutors".

Data Architecture

Strength
Database per service with versioned migrations

auth_db and tutor_db each have one owner, schemas are managed by Flyway, and Hibernate only validates. No table is written by two services.

Risk
Tutor data is split across contexts with no defined source for the read model

A tutor listing needs the name and email from auth_db.users and the bio from tutor_db.tutor_profiles. Nothing in the architecture joins them: there are no claims, events or API calls for it. The frontend already assumes the joined shape (types/tutor.ts), so this missing decision shows up as Risk 2 in the code map.

Concern
No cross-database consistency, retention or deletion path

tutor_profiles.user_id can point at a deleted or blocked user indefinitely. refresh_tokens is never cleaned up, and its revoked and last_used_at columns are never written. There is no user-deletion path.

Concern
Inconsistent types and normalisation

refresh_tokens uses TIMESTAMP while all other tables use TIMESTAMPTZ. SubjectService checks for duplicates on the trimmed name but stores the untrimmed one, and its slug generator replaces single spaces only (SubjectService.java:29-46,63).

Cost Efficiency (FinOps)

Strength
Small, self-hosted footprint

Three small containers and one shared Postgres run on a self-hosted Coolify/Forgejo stack, with no paid cloud services or per-request external calls. Runtime images are slim (JRE-only, Next.js standalone).

Concern
Redundant CI work

CI runs ./mvnw test, and then the Dockerfile runs ./mvnw verify again inside the image build, so every Java pipeline runs its tests twice. Each job also runs apt-get install docker.io. Both waste CI minutes and slow feedback.

Operability

Strength
Documented intent and a code map

The README explains the service split and its rationale, and docs/code-map.md now records flows, entry points, risks and the deployment state.

Concern
Deployment knowledge lives in the Coolify UI

The exposure, routing, environment values and secret storage of the running deployment cannot be determined from the repo, and the owner could not confirm them. There are no runbooks, no rollback procedure, no alerting and no dashboards.

Concern
Routine tasks have no procedure

Granting TUTOR or ADMIN, unblocking a user and rotating JWT_SECRET have no defined procedure. Today each would need direct database or environment access.

Deployment Architecture

Strength
Independent, immutable, per-service pipelines

Each deployable has its own workflow with path filters, a test gate and an image tagged with the commit SHA. Dockerfiles are multi-stage and run as non-root users. Services deploy independently through separate Coolify webhooks.

Risk
Two divergent deployment definitions

CI builds and pushes images, while docker-compose.coolify.yml builds from source and has no image: references. The two set different build-time values for NEXT_PUBLIC_API_URL (/api/v1 vs http://localhost:18081/api/v1), which is inlined into the browser bundle. What actually runs depends on which path Coolify uses, which is open.

Concern
No post-deploy verification or explicit rollback

Every push to main deploys straight away through a webhook, with no smoke test, health gate or promotion step. Rolling back means manually redeploying an older SHA tag in Coolify. Environment configuration is kept in Coolify, not as code.

Architecture Governance

Strength
Key decisions have stated rationale

The README explains why identity is a separate service, why the backend is a resource server, and why each service owns its database.

Concern
No ADRs, and the documentation has drifted from the code

There is no ADR directory. The README diagram shows the frontend talking to both services and calls the backend "functional and tested", but no browser path reaches auth-service and issued tokens cannot be used against the backend. Token transport, signing keys and tutor data ownership are undocumented decisions.

Domain Architecture

Strength
Services are split by business capability

Identity and access (auth-service) and the tutoring catalogue (backend) are distinct bounded contexts, rather than a technical split by layer.

Concern
No context map for concepts that span both contexts

"Tutor" spans both contexts: the TUTOR role belongs to identity, the profile to the catalogue, and the display name to identity. Nothing defines how a user becomes a tutor, which context is upstream, or how catalogue reads identity data. The result is a profile endpoint that requires a role nobody can obtain.

API Architecture

Strength
Versioned backend API with a consistent error body and OpenAPI

Backend routes live under /api/v1. Both services return the same ApiError shape (timestamp, status, error, message, path, validationErrors). springdoc publishes an OpenAPI document for the backend.

Risk
Undetected consumer/provider drift

The frontend's TutorSummary (id, email, firstName, lastName, bio) does not match the backend's TutorSummaryResponse (id, userId, bio). TutorCard.tsx:24 will throw as soon as one profile exists. No generated client, schema validation or contract test would catch this.

Concern
Auth API is unversioned and undocumented, and list APIs lack pagination

/auth/* has no version prefix and no OpenAPI. It returns empty bodies, so the API does not describe its cookie contract. Collection endpoints have no pagination or filtering, and errors outside the advice fall back to Spring's default format.

Architecture Fitness Metrics

Concern
No automated architectural checks

There are no ArchUnit or dependency rules, no API contract tests, and no check that the frontend's types match the backend's OpenAPI. CI runs only unit/slice tests, lint and build. Several findings in this review (layer leak, contract drift, dead configuration) could each become a one-line automated rule.

Common Anti-Patterns

Strength
Avoids the shared database, the distributed monolith and the shared-library trap

No tables are shared, there are no synchronous call chains between services, there is no shared library, and each service deploys independently.

Concern
Lock-step change risk through the shared secret and duplicated enum

Changing roles, claims, algorithm or key requires coordinated releases of both services. This is a narrow but real form of distributed-monolith coupling.

Concern
Mild leaky abstraction in responses

TutorProfileResponse and SubjectResponse mirror their entity columns one-to-one, including internal userId and audit timestamps. Any schema change therefore becomes an API change.

Testability

Strength
Injectable design with tests on both services

Constructor injection is used throughout via @RequiredArgsConstructor, and the CurrentUserProvider seam keeps services testable. Each service has controller and service tests, and auth-service has a JwtAuthenticationFilter integration test.

Risk
Shipped schema is never tested

Both application-test.yaml files run on H2 with flyway.enabled: false and ddl-auto: create-drop, so Hibernate generates its own schema in tests. The Flyway migrations and the production ddl-auto: validate check never run before deployment, and mismatches such as the TIMESTAMP vs Instant difference first appear at startup in the deployed environment.

Concern
No cross-service or frontend tests; time is not controllable

No test checks that a token issued by auth-service is accepted by the backend, which would have caught the transport mismatch. The frontend has no tests. JwtService and RefreshTokenService call Instant.now() directly instead of an injected Clock, so expiry cannot be tested deterministically.

Evolvability

Strength
Internals can change behind DTOs and a versioned path

Mappers and records decouple the persistence model from the API, and the /api/v1 prefix leaves room for v2.

Concern
Environment behaviour is hard-coded

The cookie Secure flag, the CORS origin and the build-time API URL are compiled into code or bundles. Moving between the LAN, staging and a future public environment means code changes or rebuilds, not configuration.

Concern
No extension point for roles or the tutor lifecycle

Roles are enums fixed at registration, and no workflow exists for changing them. Adding onboarding (apply as a tutor, approval) or bookings later has no seam to attach to.

Architectural Smells (codebase review only — not applicable in design review)

Strength
No god services or smart UI

The largest classes are under about 100 lines, and every service class has one feature's responsibilities.

Concern
Anemic domain model

Entities are data holders. Rules such as name normalisation, slug generation and status checks live in services or are missing. The only behaviour method, Subject.Deactivate(), is unused and wrongly capitalised. This is acceptable at the current size, but rules like "a blocked user cannot log in" belong on the entity.

Concern
Dead security configuration

JwtAuthenticationConverterConfiguration declares a converter method without @Bean, which duplicates the JwtAuthenticationConverter component actually in use. Readers cannot tell which converter applies.

Recommended Architecture

No revised System Context diagram is included because the system boundary and its actors are sound. The changes below are inside and between the containers. The targets are recommendations for evolving from the current LAN/test setup; they are not requirements of it.

Recommended Sequence — login, call, refresh

Change: the cookie is first-party and accepted by the backend, with CSRF protection. Expiry is handled by a refresh with rotation instead of a hard logout.

  1. Settle token transport, then fix it end to end. Fixes Security Risk 1 and the Separation of Concerns, Layered and Hexagonal findings. Recommended option: serve /auth and /api/v1 from the frontend's origin, and give the backend a BearerTokenResolver that reads the access_token cookie (with the header as a fallback for tools) and turns CSRF protection back on for the cookie path. Move cookie writing out of AuthService into a delivery adapter. Record the choice in an ADR.
  2. Replace the shared HS256 secret with asymmetric keys and JWKS. Fixes the Security and Coupling risks. auth-service signs with RS256 or ES256 and a kid, and the backend uses NimbusJwtDecoder.withJwkSetUri and validates iss and aud. Rotation becomes "publish a new key, sign with it, retire the old key after the token TTL", and the backend can no longer mint tokens.
  3. Define the tutor read model and enforce the API contract. Fixes the Data, Domain and API risks. Add name claims to the access token and snapshot display_name into tutor_profiles at creation, or explicitly drop names from the UI. Generate the frontend client and types from springdoc's OpenAPI, validate responses with zod, and fail CI on drift.
  4. Complete the identity lifecycle. Covers the Security, Operability, Domain and Evolvability findings:
    • check UserStatus at login;
    • add /auth/refresh with rotation and reuse detection, and /auth/logout;
    • clean up expired refresh tokens on a schedule;
    • rate-limit login;
    • add an admin API for role and status changes;
    • turn auth-filter failures into 401s.
  5. Add repeatable, environment-gated dev/test provisioning. Add a profile-gated ApplicationRunner or a separate Flyway location (for example db/seed-dev) that creates TUTOR and ADMIN test accounts from environment-supplied credentials, so recreating the database restores them. Keep it disabled in any production profile.
  6. Raise test fidelity and add fitness functions. Covers the Testability and Fitness Metrics findings:
    • run tests against Postgres via Testcontainers with Flyway on and ddl-auto: validate;
    • add one cross-service test that issues a token in auth-service and has the backend accept it;
    • inject a Clock;
    • add ArchUnit rules (no jakarta.servlet in ..service.., no entities in controllers);
    • add frontend type and contract checks.
  7. Make the deployment one explicit definition. Covers the Deployment Architecture, Security network and Reliability findings:
    • point docker-compose.coolify.yml at the CI image SHA tags, or delete it if Coolify uses separate image resources;
    • keep NEXT_PUBLIC_API_URL relative;
    • make BACKEND_INTERNAL_URL a true runtime setting or document that it needs a rebuild;
    • expose only the proxy port with TLS;
    • add container healthchecks;
    • add a post-deploy smoke test;
    • stop running tests a second time in the Dockerfile.
  8. Give secrets and databases clear ownership. Covers the Security and Operability findings. Create a separate database user per service with access only to its own database, commit a .env.example that lists variable names only, record the single source of truth for each secret, and document the rotation procedure.
  9. Add baseline observability. Covers the Observability findings. Add structured logs with a request ID for authentication events, authorization denials and unhandled errors (never passwords or tokens), a catch-all advice that keeps the ApiError shape, a mapping from DataIntegrityViolationException to 409, and a Prometheus metrics endpoint.
  10. Clean up the data and the code. Covers the Data Architecture and Smells findings. Migrate refresh_tokens to timestamptz, fix subject name trimming and slug generation, add pagination before list sizes grow, remove JwtAuthenticationConverterConfiguration and the unused Subject.Deactivate(), and handle errors in FeaturedTutorsSection.
  11. Start ADRs and keep the README in step with the code. Covers the Governance findings. The first ADRs should cover token transport, signing keys, tutor data ownership and the deployment definition.
  12. Preserve these strengths: database-per-service, no synchronous calls between services, stateless services, the CurrentUserProvider port, the mapper and DTO layering, one shared error body, and independent per-service pipelines.

Migration Notes

1. Make change safe first. Do recommendation 6 before anything else: Testcontainers with Flyway, the cross-service token test, and the frontend contract check. Every later step changes a contract, and today none of those contracts is tested.

2. Unblock the core flow. Next, do recommendation 1 (single origin, cookie resolver plus CSRF) together with the UserStatus check and the profile-gated seed (recommendation 5). At that point a tutor can log in and create a profile from the web app. Then fix the tutor read model (recommendation 3) so listing tutors stops crashing.

3. Harden identity. Then add refresh and logout, rotation, rate limiting and the admin role API (recommendation 4). After that, migrate to JWKS (recommendation 2). JWKS is easiest to land once tokens are already refreshable: deploy auth-service publishing both keys, switch the backend to JWKS, start signing with the new key, and remove JWT_SECRET once the old tokens have expired.

4. Operational foundation. Recommendations 7–9 can run in parallel with the steps above. Each is local to one file or configuration area and carries little risk on a LAN deployment. Recommendations 10–11 are ongoing hygiene.

Everything here assumes the current LAN/test environment. Before any public exposure, steps 1–3, TLS, per-service database users and backups are prerequisites.
